# BiliCinema 仅观影与私人同步房间

## Windows 本地运行

1. 在仓库根目录双击 `Start-Watch.cmd`。脚本从当前源码构建并打开仅观影窗口，需要 .NET 10 SDK 和 Windows WebView2 Runtime；不需要 mpv。首次运行需要等待依赖还原和编译。
2. 扫码登录，粘贴 B 站番剧或电影剧集链接，点击“解析”，再点击“在线播放 / 继续”。影片显示在软件窗口内。软件把本机登录 Cookie 交给独立的私密网页播放器会话，播放器从 B 站自行请求音视频片段；本软件不再为观影模式解析 DASH 直链或启动独立播放器。
3. 在视频画面内选择 B 站提供的画质、音轨和音量。窗口会显示实际解码分辨率。4K 是否出现取决于 B 站对此账号、影片和嵌入式播放器的授权；不能仅凭影片详情或已登录状态保证 4K。
4. 观影窗口保留播放、暂停、进度跳转和倍速控制。房间只转发影片 ID 和控制状态，每台设备都以自己的登录状态在本机播放。房主解析影片后点“创建房间”“复制邀请”，另一端粘贴邀请并加入；双方准备好后由房主控制同步。
5. “离开房间”停止本次播放但保留登录。“退出本机账号”清理当前数据目录中的登录信息及网页播放器内的 B 站 Cookie。窗口只加载 B 站官方嵌入式播放器地址，不开放站内其他页面或弹窗。

测试两台本机客户端时，可为每个实例指定独立数据目录：

```powershell
./script/start-watch.ps1 -DataDir ./artifacts/test-account-a
./script/start-watch.ps1 -DataDir ./artifacts/test-account-b
```

`DOWNKYI_DATA_DIR` 是已有的数据目录覆盖入口；网页播放器的私密会话也按该目录隔离。普通 DownKyi 下载模式仍从原程序入口启动。

## 房间服务

本机联调可双击仓库根目录的 `Start-Room-Server.cmd`，或运行 `./script/start-room-local.ps1`，默认地址为 `ws://127.0.0.1:5077/ws`。访问 `http://127.0.0.1:5077/health` 可确认服务已启动。房间服务只保存内存中的房间码、成员 ID、影片标识和播放状态；它不转发视频。关闭服务会结束所有房间。

房间服务窗口是后台同步服务，观影界面由 `Start-Watch.cmd` 打开。同一台电脑本机联调可在观影窗口使用 `ws://127.0.0.1:5077/ws`。两台异地电脑填写各自的 `127.0.0.1` 无法加入同一个房间。

异地使用时，服务可运行在两人其中一台电脑上，只要另一台能连接到它。服务自身仍只监听 `127.0.0.1:5077`，同机通过支持 WebSocket 的 TLS 反向代理提供 `wss://你的域名/ws`。两端填写同一个 `wss` 地址。`src/DownKyi.RoomServer/README.md` 给出 Caddy 示例、协议和连接限制；客户端拒绝远程明文 `ws`。

## 播放与验证边界

- 观影模式使用 B 站官方 `player.bilibili.com/player.html` 嵌入式播放器及 Windows WebView2。网页播放器管理缓冲、分片、码率和音轨；它与完整 B 站页面可能有不同的画质权限或交互。没有完整影片文件下载任务。
- 启动、跳转或网络中断时，缓冲行为由网页播放器决定。客户端读取 HTML 视频元素的位置、时长、分辨率和缓冲状态，用于房间同步；连接异常时最多重新打开两次并尝试恢复时间位置。
- 已验证 Windows Release 严格构建、仅观影窗口能启动。尚未完成登录账号下的实际影片连续播放、4K、双设备房间同步和异地 `wss` 验收。桌面测试 82 项中有 80 项通过；另外两项关于普通下载详情页的视图结构断言失败，该页面未在此轮修改。
- 实际验收时，两端分别扫码播放同一影片，在画面菜单确认可用画质，观察窗口显示的实际解码尺寸和声音；连续播放一段时间，再跳到未缓冲位置并跳回。随后加入同一房间，检查房主暂停、恢复、跳转和重连后的时间差。不能把本机窗口启动或信令检查视为已验证异地观影。
