最终交互约定（优先于原图文字和下附生成提示词）
- 房主决定云端时间轴。访客加入、尚未就绪、缓冲、进入后台或掉线，只影响该访客本机；房主和其余访客继续播放。访客恢复后对齐房主当前进度，不追赶过期快照，也不在每次快照到达时强制 seek。
- 房主未就绪或缓冲时全房暂停，并保留此前的播放请求；房主恢复后自动继续。房主主动暂停会清除播放请求。房主掉线沿用两分钟重连窗口，重连后由房主明确重新发起播放。
- 每个成员仍须如实报告 ready/buffering，保持精确影片与分 P 身份校验、房主权限和五人上限；访客不阻塞不意味着伪报就绪或绕过校验。
- 新消息在画面右侧短暂显示“昵称＋消息内容”，以纯文本展示 5 秒，与 Windows 保持一致；聊天面板继续用于查看完整消息和发送文字。原图仅靠聊天入口未读点提示新消息的方案已被这项讨论结果替代。

一、原始调查基线（改造前；不是当前实现说明）
1. 启动时直接加载 https://www.bilibili.com，使用 Windows/Chrome 桌面 UA 和宽视口。首页、登录和视频共用同一 WebView。
   入口：android/app/src/main/java/com/leonz03/bilicinema/MainActivity.java:61,74,117,199,244。
2. 播放页通过 player.js:43 的 fitPlayer 隐藏播放器祖先的其他子元素。只有找到支持的 video/root 才生效；首页和登录页没有这条隔离保证。页面加载过程和 DOM 变化也可能露出整页。
3. player.js:88 将所有 video.play() Promise 拒绝合并为 blocked，没有保留原因分类。MainActivity.java:135,267 将 blocked 和真实播放器错误一并处理为 MediaSession.ERROR；MediaSession.java:30,38 之后忽略播放器观测，不能仅靠后续 ready 事件恢复。
4. cloud/src/cloud-room.mjs:121,326,333 按所有在线成员 ready 且非 buffering 控制播放；访客不就绪或缓冲会暂停整房。与上面的本地错误处理组合，会形成“播放→访客失败→撤销就绪→整房暂停”的故障放大链。
5. 影片身份依赖 window.player / bilibiliPlayer 的 getCid。接口缺失时脚本发送 CID=0，即使存在可播的 video；MediaSession 会等待或撤销身份验证。不能以删除身份校验或伪报 ready 修复。
6. MediaSession 对 readyState、waiting、stalled 逐事件门控；MainActivity 在就绪恢复时强制套用快照；player.js 使用固定 1800ms 抑制控制回声。短时缓冲、seek 与异步事件的交错存在抖动和意图误识别风险，需真机时序确认。
7. MainActivity.java:84 的 buildUi 将登录、更新、选片、房间、控制和聊天堆叠在一个长滚动页面；横屏只改变播放器高度，缺少场景和设备布局。

二、原始调查的证据边界
- 已运行现有 5 项 Node 播放脚本测试，全部通过。
- 只读 VM 模拟确认两点：play 拒绝只剩 blocked 分类；无预期页面 API 时 video 就绪仍报告 CID=0。
- 未连接可调试安卓设备；以上不等于在用户手机上重现了确切触发。需要脱敏事件与房间快照确认是 autoplay/编解码/鉴权、身份识别、缓冲抖动中的哪一个。
- 应采集事件类型、错误名、readyState、相对时间、角色、短期 generation、snapshot.version/syncRevision/playing/waitingForReady 及各成员 ready/buffering。不得记录 Cookie、token、账号标识、完整敏感 URL 或私有重连凭据。
- 代码/协议测试通过不能替代真机播放、登录和旋转验收。

三、设计方向与最终同步约定
A. 播放：
优先验证本机按账号权限解析媒体并交给 Android Media3 的可行性，先普通稿件，再分 P 和会员/番剧兼容性。原生播放直接提供准备、缓冲、实际播放、错误和用户意图的状态。WebView 放在独立登录流程或明确标识的兼容流程中，不再作为首页。
Media3 不自动获得 B 站权限或 DRM license；实际格式、设备解码和内容授权仍须验证。不能承诺所有内容可播，也不向云端上传凭据或媒体地址。
如果仍保留网页播放，未确认播放器区域时应显示原生加载/错误层，而不是裸露完整网页；对 DOM 和身份接口的依赖仍然存在，必须明确兼容范围。

B. 同步：
沿用并修复既有 MediaSession 状态所有权，不增加并行状态中心。区分加载、可播、缓冲、需要本地点按、需要登录、可重试网络错误、不可播放、重连。
保留房主播放意图与真实缓冲门禁；不要把一次本地播放失败永久封死，也不要把程序施加的暂停误写为房主主动暂停。
本地准备/手势确认后才发布真实就绪；保持精确影片与分 P 校验。
采用房主控制、访客追随：只有房主真实未就绪或缓冲才暂停全房，并保留播放意图；主动暂停清除意图。访客准备、缓冲、后台或掉线不阻塞其他成员，恢复后追随房主当前进度。访客本机失败给出重试或检查登录等操作，聊天仍可使用。
沿用现有 v2 成员状态字段表达真实 readiness，不增加“暂不参与同步”协议标记，也不以伪报 ready 避开门禁。云端与 Windows、Android 必须对房主门禁和访客恢复使用一致语义。
控制事件应依据当前媒体 generation、快照版本和操作来源避免回声；短时缓冲合并需要用真机数据决定，不能通过忽略真实缓冲制造假就绪。

C. UI：
首页只保留选片、建房、加入、恢复有效房间与账号入口；不默认打开 B 站主页。
房间以视频为主，影片、同步状态、成员和聊天围绕观看；设置与软件更新收入账号/更多菜单。
手机竖屏是 16:9 视频加下方聊天；横屏全屏，控制浮层按需显示、聊天按需打开；平板是视频与房间侧栏并排。16:9 视频保持比例，宽屏允许黑边，不拉伸内容。
账号/官方登录单独成页。“我已完成登录”触发本地实际登录态核验，不能仅凭按钮点击标记登录成功。图中二维码仅作示例，不可使用。
只提供文字聊天，图中头像为虚构示例；不得默认把 B 站账号身份公开给房间。成员显示名是房间昵称，需按协议验证。
房主才能换片、播放、seek 和调倍速；访客显示跟随房主，保留音量、清晰度、全屏和本地点按等本机能力。
房主等待、访客本机加载失败、需要点击启用都保留房间上下文，聊天可用。状态原因显示在相关位置，给出对应操作，不堆叠全局错误文字；访客本机问题不显示为全房等待。
右侧新消息提示同时显示房间昵称和消息内容，纯文本展示 5 秒；控制浮层或聊天面板的重复刷新不重新延长同一消息的提示时间。

四、视觉规则
品牌：沿用已有青色品牌方向，只使用 BiliCinema 文字标识，不生成替代 Logo。
颜色：背景 #101216；表面 #1A1E25；分隔 #303642；主文字 #F4F6FA；次文字 #A8B2C3；强调青 #64C9DF；就绪 #66D6AF；等待 #F4C478。
控件：4/8dp 间距体系，手机 20dp 侧边距，卡片约 16dp 圆角，安卓触控目标至少 48dp。状态同时用图标和文字，不只靠颜色。
字体：系统中文无衬线；适应系统字号和屏幕阅读器；确保安全区、键盘和固定输入栏不会遮挡内容。
风格：炭黑影院感、克制青色、清楚层级；无大面积炫光、复杂渐变或网页导航。
本地设计库未匹配到 watch-party 专用模板，未采用检索结果中的影院订票/营销漏斗；本稿使用与场景相符的通用 Android 交互原则。
图像只是视觉定稿，尺寸、对比度、TalkBack、大字号和横竖屏还须在实际实现中验收。

五、落地前验收
同一版本下验证 Windows 房主+Android 访客、Android 房主+Android 访客以及混合五人：
进入房间、房主就绪后起播、加载期间发起播放、真实缓冲与恢复、分 P/换集、seek、后台/前台、断网重连、登录过期、会员与不支持内容、旋转和聊天键盘。
播放失败应可恢复；房主意图不丢失；不允许旧影片事件污染新影片或伪报就绪。
确认访客加入、未就绪、缓冲、后台或掉线均不暂停房主与其他访客，恢复后对齐当前房主；确认房主缓冲时全房暂停、恢复续播，主动暂停后不会自动重启。确认右侧消息提示包含昵称和内容，5 秒后消失。
